# FundiBolt Security Review

Point-in-time review of `code/backend` and `code/mobile` as of this commit. Scope: authentication/OTP flow, authorization on bookings/conversations/technician data, data handling, and mobile client practices. This is not a substitute for a professional penetration test or a dependency-vulnerability scan (`npm audit`) — both are still recommended before any public/production launch.

Severity is rated by realistic impact at the current stage (small user base, no live payments yet), not worst-case theoretical impact.

## Fixed in this patch

| # | Finding | Severity | Fix |
|---|---|---|---|
| 1 | `generateOtp()` used `Math.random()`, which is not cryptographically secure and is unsuitable for anything that gates account access. | Medium | Switched to `crypto.randomInt` (Node's CSPRNG) — same pattern already correctly used by `generateTempPassword`. |
| 2 | The dev OTP bypass (`DEV_BYPASS_CODE`) was gated only on `NODE_ENV === "production"`. Any environment reachable by real users that doesn't have `NODE_ENV` set to *exactly* that string (a typo, a different casing, a staging environment, a platform that doesn't set it) would silently leave a universal `123456` OTP bypass active. | **High** | Added a second, independent required flag: `ENABLE_DEV_OTP_BYPASS=true`. The bypass now fails closed by default — a missing/wrong `NODE_ENV` alone can no longer accidentally leave it on. **Action needed:** add `ENABLE_DEV_OTP_BYPASS=true` to your local `.env` to keep the dev convenience working. |
| 3 | No rate limiting existed on `/api/auth/login`, `/api/auth/signup`, `/api/auth/forgot-password`, or any `/api/otp/*` endpoint — all were open to unlimited brute-force/credential-stuffing/spam attempts. | **High** | Added an in-memory, per-IP-and-route fixed-window limiter (`src/middleware/rateLimit.ts`) applied to all five endpoints. See its doc comment for the tradeoff (per-instance, not shared across a multi-instance deployment) and when to swap in a Redis-backed one. |
| 4 | Server-side password minimum was 6 characters, well below current guidance (NIST SP 800-63B treats 8 as a reasonable floor), and had no relationship to the mobile app's own client-side strength meter — meaning anyone calling the API directly (curl/Postman) could bypass the app's guidance entirely. | Medium | Raised server minimum to 8 on both signup and change-password. Updated the mobile change-password modal's matching client-side check and copy for consistency. |

## Recommended, not yet implemented

These are real findings but were judged too invasive, too uncertain without a live environment to verify against, or too dependent on a business decision to make unilaterally in this patch. Ordered roughly by priority.

| # | Finding | Severity | Why it matters | Suggested fix |
|---|---|---|---|---|
| 5 | `POST /api/auth/signup` returns `409` with a message confirming an account already exists for a given email/phone. `forgotPassword` deliberately avoids this exact pattern (always returns the same generic message) for good reason. | Medium | Allows enumerating registered emails/phone numbers one at a time. Now partially mitigated by the new signup rate limiter, but not closed. | Either accept the tradeoff (many apps do, for UX reasons) and rely on rate limiting alone, or change signup to also return a generic "check your email" response regardless, and only reveal the conflict via the email itself. This is a product decision, not just a code fix. |
| 6 | Avatar upload (`config/upload.ts`) validates file type using the client-supplied `mimetype` field only — this is attacker-controlled (just a header on the multipart part) and easy to spoof. No magic-byte/content sniffing is done. | Medium | A file with a spoofed `Content-Type: image/jpeg` but arbitrary actual content could be accepted and stored. Files are served statically (not executed), which limits impact, but this is still a real gap for a "verify what you're actually storing" standpoint. | Add a magic-byte check (e.g. the `file-type` npm package) after upload, before accepting the file, in addition to the existing mimetype/extension check. |
| 7 | JWTs are valid for 7 days with no revocation mechanism — a leaked token stays valid for its full lifetime regardless of a password change, logout, or suspected compromise. | Medium | No way to force-invalidate a session short of rotating `JWT_SECRET` (which invalidates *every* session at once). | Either shorten the token lifetime and add a refresh-token flow, or add a `tokenVersion` column on `User`, embed it in the JWT payload, and check it on every `requireAuth` call — bump it on password change/logout-everywhere to invalidate just that user's existing tokens. |
| 8 | `bcrypt` cost factor (`SALT_ROUNDS`) is 10. Current guidance commonly recommends 12+ as hardware has gotten faster since 10 became the old default. | Low | Not urgent, but hashing speed has a direct relationship to brute-force cost if a database were ever exfiltrated. | Bump `SALT_ROUNDS` to 12. Non-breaking — bcrypt hashes are self-describing (the cost factor is stored in the hash itself), so existing hashes keep working; only newly-set passwords use the new cost. |
| 9 | CORS is fully open (`cors()` with no origin restriction). | Low (currently) | Low real risk today since the API uses Bearer tokens, not cookies, and the only client is a native mobile app (not subject to CORS at all). Becomes more relevant once the web admin dashboard (`code/admin`) exists and if it ever uses cookie-based auth. | Scope `cors()` to an explicit allow-list of known origins once the admin dashboard's real domain is known. Not urgent before then. |
| 10 | No shared `requireRole` middleware exists — role checks are done ad hoc, inline, per controller (correctly, everywhere it's currently needed, e.g. `updateMyLocation`'s `fundi`-only check). | Low | Works correctly today, but as more role-gated endpoints are added, an inline check is one omitted `if` away from a real authorization bug — a shared, tested middleware is harder to forget. | Add `requireRole(...roles)` to `middleware/auth.middleware.ts` and migrate existing inline checks to it opportunistically. |
| 11 | Uploaded files (avatars) are stored on local disk (`UPLOADS_ROOT`), not in object storage (S3/R2/Supabase Storage/etc). | Low (availability, not a vulnerability) | Most hosting platforms have ephemeral or single-instance-only disks — uploads can silently disappear on redeploy, and this can't scale past one server instance. | Move to object storage before any real deployment beyond a single dev/staging box. |
| 12 | CI (`ci.yml`) runs lint/typecheck/tests but no dependency vulnerability scan. | Low | Wouldn't catch a known-vulnerable transitive dependency landing in the tree. | Add an `npm audit --audit-level=high` step. Not added automatically in this patch since the current dependency tree may already have pre-existing findings (e.g. `eslint@8.57.1` is end-of-life) that would need triaging first to avoid immediately red-lighting CI. |

## Reviewed and found sound (no action needed)

Worth recording so future reviews don't need to re-check these from scratch:

- **Booking and conversation ownership checks** (`booking.controller.ts`, `conversation.controller.ts`): every read/write correctly verifies the requesting user is the customer or technician on that specific record before allowing access — no IDOR (Insecure Direct Object Reference) found. IDs are UUIDs, but access control doesn't rely on that for its security, which is the correct posture.
- **`forgotPassword`**: always returns the same generic response regardless of whether the identifier matched an account — correctly avoids enumeration (contrast with finding #5 above).
- **`login`**: returns a generic "Invalid credentials" for both wrong-email and wrong-password cases — doesn't help an attacker distinguish which part was wrong.
- **JWT payload**: contains only `{ userId, role }` — no sensitive data exposed via token decoding (JWTs are signed, not encrypted, and trivially decodable by anyone holding one).
- **Token storage on mobile**: the JWT is kept only in React state, not persisted to `AsyncStorage` or similar — so there's no at-rest-on-device storage to worry about. (Tradeoff: every app restart requires re-login — a UX cost, not a vulnerability, and a reasonable one at this stage.)
- **`.env` files**: correctly excluded from git via `.gitignore`; only `.env.example` (placeholders, no real secrets) is committed.
- **`generateTempPassword`**: already correctly uses `crypto.randomBytes` (unlike the OTP generator before this patch — see fix #1).
